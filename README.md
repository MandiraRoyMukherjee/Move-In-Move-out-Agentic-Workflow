# ANACITY Move-In / Move-Out Agentic Workflow

AI-assisted, stateful, rule-aware, human-in-the-loop move request management for residential communities.

## Overview

ANACITY replaces paper-based or email-driven move-in/move-out workflows with an AI-guided conversational experience. Residents describe their move in natural language; the agent collects information, validates against community-specific rules, and submits a structured request for admin review. Admins see an AI-generated summary and recommendation, then make the final decision.

## Features

- **AI move-in assistant** — natural language input, structured data extraction, one-question-at-a-time flow
- **AI move-out assistant** — notice period enforcement, 7-day rule validation, alternative date suggestions
- **Community rule validation** — day/time/notice period rules stored in DB, not hardcoded
- **Admin dashboard** — stats, filterable request table, full request review
- **AI assessment** — per-request summary and recommendation generated by Groq LLM
- **Human-in-the-loop** — admin approves/rejects/requests-more-info; AI cannot act autonomously
- **Resident resubmit** — after admin requests info, resident provides it and re-enters review
- **Audit trail** — every action logged with actor, timestamp, and details
- **Error recovery** — LLM failure preserves request state; structured form fallback

## Architecture

```
NATURAL LANGUAGE
      ↓
    AGENT  (Groq llama-3.1-8b-instant)
      ↓
 ┌────────────┼────────────┐
 ↓            ↓            ↓
CONTEXT    COMMUNITY    STATE
            RULES
 └────────────┼────────────┘
              ↓
         VALIDATION  (deterministic TypeScript/Zod)
              ↓
       HUMAN CONFIRMATION
              ↓
         ADMIN DECISION
              ↓
            AUDIT
```

## Agent Design

**LLM responsibility** (Groq `llama-3.1-8b-instant`):
- Understand natural language
- Extract structured data (dates, times, names)
- Generate human-readable questions for missing fields
- Produce request summaries and admin recommendations

**Application responsibility** (TypeScript, never the LLM):
- Validate dates against community rules
- Check notice periods
- Enforce allowed days/times
- Transition request statuses
- Update the database
- Approve or reject requests

This separation is enforced architecturally — the LLM output feeds into a validation layer before any DB write occurs.

## Database

Four entities:

- **Community** — name + JSON config (move-in/move-out rules)
- **Resident** — name, email, phone, apartment, community
- **MoveRequest** — full request data, conversation state, agent summary
- **AuditLog** — every action with actor, type, and details

SQLite for development. Switch to PostgreSQL by changing the Prisma adapter in `src/lib/db/prisma.ts` — no business logic changes required.

## Local Setup

### Prerequisites

- Node.js ≥ 20
- A [Groq API key](https://console.groq.com) (free tier)

### Steps

```bash
git clone <repo-url>
cd anacity-move-workflow
npm install
```

Copy the environment template:

```bash
cp .env.example .env
```

Edit `.env` and set your Groq API key:

```
DATABASE_URL="file:./prisma/dev.db"
GROQ_API_KEY="gsk_your_key_here"
```

Run migrations and seed:

```bash
npx prisma migrate dev
npx tsx prisma/seed.ts
```

Start the dev server:

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

## Environment Variables

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | SQLite file path or PostgreSQL connection string |
| `GROQ_API_KEY` | Groq API key (server-side only, never exposed to browser) |

## Example Scenarios

### Scenario 1 — Successful Move-In
1. Resident → Move In → select John Doe
2. Type: "I want to move in next Saturday at 10 AM"
3. Agent collects missing info (moving company, vehicle)
4. Resident confirms → submits
5. Admin → reviews → approves
6. Resident sees APPROVED status

### Scenario 2 — Rule Violation (Sunday / Late Night)
1. Type: "I want to move in Sunday at 8 PM"
2. Agent extracts date/time → validation catches Sunday + 8 PM violation
3. Agent explains and suggests next valid date

### Scenario 3 — Move-Out Notice Period
1. Resident → Move Out → select Jane Smith
2. Type: "I want to move out tomorrow"
3. Validation catches 7-day notice requirement
4. Agent explains and suggests earliest valid date

### Scenario 4 — Admin Requests Information
1. Admin opens request → clicks "Request More Information"
2. Resident sees message on their request detail page
3. Resident provides info → request returns to UNDER_REVIEW

## Deployment

See [Vercel Deployment](#vercel-deployment) section below.

### Vercel Deployment

1. Push to GitHub
2. Connect repo in Vercel
3. Add environment variables:
   - `DATABASE_URL` — use a hosted SQLite (Turso) or PostgreSQL (Supabase)
   - `GROQ_API_KEY`
4. Deploy

> **Note:** SQLite file-based storage doesn't persist across Vercel serverless invocations. For production use Turso (libsql) or Supabase (PostgreSQL). The Prisma adapter in `src/lib/db/prisma.ts` is the only file that needs changing — all business logic stays the same.

## Limitations

- Authentication is simplified (resident selector dropdown). Production requires real auth + RBAC.
- SQLite is for development only. Use Turso or PostgreSQL for production.
- No file/document upload (referenced in schema, not implemented in UI).
- No email notifications.

## Production Considerations

| Concern | Solution |
|---------|---------|
| Database | PostgreSQL (Supabase/Neon) via `@prisma/adapter-pg` |
| Authentication | NextAuth / Clerk with role-based access |
| Rate limiting | Middleware on `/api/agent/*` routes |
| Observability | Vercel Analytics + structured logging |
| Notifications | Email via Resend/SendGrid on status changes |
| Document storage | Vercel Blob / S3 |
| Model monitoring | Log LLM inputs/outputs to audit table |
