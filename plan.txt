# ANACITY Move-In / Move-Out Agentic Workflow

## AI Coding Agent Development Plan

## 1. Objective

Build a polished working prototype for the ANACITY Move-In / Move-Out Agentic Workflow assignment.

The application must support:

1. Resident experience

   * Move-In request
   * Move-Out request
   * AI-assisted request creation
   * Request validation
   * Request submission
   * Request status tracking

2. Administrator experience

   * Admin dashboard
   * View pending requests
   * Review complete request context
   * View community rules
   * View AI-generated assessment/recommendation
   * Approve request
   * Reject request
   * Request additional information
   * Add admin notes

3. Agentic workflow

   * Natural-language understanding
   * Context/state management
   * Missing information detection
   * Community rule retrieval
   * Request validation
   * AI-generated summary
   * AI recommendation
   * Human-in-the-loop approval
   * Guardrails
   * Audit logging

4. Scalability

   * Community-specific configuration
   * No community-specific rules hardcoded into agent logic
   * Core workflow reusable across communities
   * Configuration-driven business rules

5. Deployment

   * GitHub repository
   * Feature-wise commits
   * Vercel deployment
   * Production environment variables
   * README with setup instructions

---

# 2. Technology Stack

Use the following technologies.

### Frontend

* Next.js
* React
* TypeScript
* Tailwind CSS
* shadcn/ui or another clean component library if useful
* Lucide icons

### Backend

Use the Next.js application itself.

* Next.js Route Handlers / Server Actions
* TypeScript
* Service-layer architecture

Do NOT create a separate backend unless technically necessary.

### Database

Use:

* SQLite
* Prisma ORM

The application must keep database access behind Prisma/repository/service layers so SQLite can later be replaced with PostgreSQL without rewriting business logic.

### AI

Use an LLM API through a server-side service.

Preferred:

* OpenAI API

But structure the code so the provider can be changed later.

Never expose the LLM API key to the browser.

### Deployment

* GitHub
* Vercel

# 6. Resident Journey — Move-In

Implement the following workflow.

## Step 1

Resident opens dashboard.

Display:

* Move In
* Move Out
* Existing requests

## Step 2

Resident selects Move In.

Open Agentic Move-In Assistant.

The user should be able to interact using natural language.

Example:

User:

"I want to move in next Saturday at 5 PM."

Agent should extract:

* request type
* date
* time

## Step 3

Agent checks the current request state.

Identify missing information.

For example:

* apartment number
* moving company
* vehicle information

Ask only for missing information.

Do not repeatedly ask for information already provided.

## Step 4

Agent checks community configuration.

Validate:

* allowed day
* allowed time
* notice period
* required information

## Step 5

If invalid:

Explain the problem clearly.

Example:

"Move-ins are allowed Monday-Saturday between 9 AM and 6 PM. Sunday at 8 PM is not available."

If possible, provide the next valid option.

## Step 6

Once complete, show a structured summary.

Example:

Move-In Request

Apartment:
A-1204

Date:
12 October 2026

Time:
5:00 PM

Moving Company:
XYZ Movers

Vehicle:
KA01AB1234

Community Rules:
✓ Date allowed
✓ Time allowed
✓ Required information complete

Buttons:

[Edit]
[Confirm & Submit]

## Step 7

After confirmation:

Create MoveRequest.

Status:

SUBMITTED

Then:

UNDER_REVIEW

Create AuditLog.

# 11. Agent Responsibilities

The agent should perform these tasks.

## Agent CAN

* Understand natural language
* Extract structured information
* Maintain conversation context
* Maintain request state
* Identify missing fields
* Retrieve community configuration
* Validate requests
* Explain rule violations
* Suggest alternatives
* Generate request summaries
* Generate admin recommendations

## Agent CANNOT independently

* Override community rules
* Approve requests
* Reject requests
* Perform irreversible actions without confirmation
* Change critical information silently

Final approval/rejection remains with the administrator.

This creates a human-in-the-loop workflow.

# 14. Important Agent Design Principle

Do NOT allow the LLM to directly control database operations.

Use:

LLM
↓
Structured intent/action
↓
Application validation
↓
Service/tool
↓
Database

For example:

LLM says:

"approve request"

Do NOT directly approve.

Instead:

LLM recommendation
↓
Admin sees recommendation
↓
Admin clicks Approve
↓
Backend validates authorization
↓
Database updated

This is a critical safety/architecture requirement.

---

# 15. AI Structured Output

Use structured JSON output from the LLM.

Example:

{
"intent": "CREATE_MOVE_IN_REQUEST",
"extractedData": {
"moveDate": "2026-10-12",
"moveTime": "17:00"
},
"missingFields": [
"movingCompany",
"vehicleDetails"
],
"nextQuestion": "What moving company will you be using?"
}

Do not rely on parsing arbitrary natural-language LLM responses for important application logic.

# 20. Agent Failure Recovery

If the LLM fails:

1. Preserve existing request state.
2. Do not lose user-entered information.
3. Show a clear error.
4. Allow the user to continue using structured fields.
5. Do not create duplicate requests.

If a database operation fails:

* show error
* do not falsely display success
* maintain request state where possible

Do NOT:

* create a generic chatbot with no workflow
* hardcode community rules inside agent prompts
* let the LLM directly update database state
* allow AI to independently approve/reject requests
* expose API keys in frontend
* lose request state between messages
* create duplicate requests
* build unnecessary microservices
* over-engineer the prototype

DO:

* make the workflow obvious
* make AI value obvious
* maintain structured state
* use community configuration
* keep deterministic logic deterministic
* provide human approval
* maintain audit history
* provide meaningful error handling
* make the prototype easy to demo

# 35. Final Principle

The prototype should communicate this architecture clearly:

```
                NATURAL LANGUAGE
                       ↓
                     AGENT
                       ↓
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       CONTEXT       RULES        STATE
          │            │            │
          └────────────┼────────────┘
                       ↓
                   VALIDATION
                       ↓
                HUMAN CONFIRMATION
                       ↓
                 ADMIN DECISION
                       ↓
                     AUDIT
```

The goal is not to demonstrate "an AI chatbot."

The goal is to demonstrate:

"An AI-assisted, stateful, rule-aware, human-in-the-loop workflow that can support different communities without changing the core application logic."
